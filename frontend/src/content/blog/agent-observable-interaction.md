## 从“能回答”到“敢使用”

智能问数早期版本已经能够根据自然语言生成报表，但用户仍然不愿意采纳结果。问题不只在模型准确率：用户不知道系统是否理解了问题，不知道指标和时间口径是否正确，也不知道结果来自哪里。发生错误时，他们更不知道应该修改什么。

因此，我把目标定义为：让 AI 结果**可理解、可干预、可验证**，而不是只追求一个离线准确率数字。最终结果采纳率从 15% 提升到 60%，并支持 5+ 家付费客户交付。

## 先拆解任务，再设计页面

我先把一次问数任务拆成完整链路：

```text
问题输入 → 意图识别 → 指标 / 维度匹配 → 时间识别 → 工具调用 → SQL 校验 → 结果解释
```

每个节点都需要回答三个问题：系统正在做什么？用户能否确认或修改？失败后能否继续完成任务？这一步将“模型不准”的笼统反馈，转化成可以被产品、算法和研发共同处理的具体问题。

## 交互原则一：把黑盒结果变成任务过程

页面不再直接返回一个最终答案，而是展示任务状态和执行步骤。已完成、进行中、需要确认、失败四种状态使用稳定的视觉语义，用户可以快速判断任务停留在哪个节点。

状态信息只展示对决策有帮助的内容，例如当前识别出的指标、时间范围、数据源和下一步动作；不展示无法验证的冗长推理文本。

## 交互原则二：在高风险节点提供干预

并不是每一步都需要用户确认。我的判断是：只有当节点会显著影响结果，且用户能够提供有效信息时，才增加干预入口。

典型的干预点包括：

- 指标存在多个口径时，展示候选指标和定义；
- 时间表达不明确时，允许修改时间范围；
- 查询失败时，解释失败类型并提供重试、编辑或切换数据源；
- 结果生成后，展示数据来源、更新时间和计算依据。

这样既避免了 Agent 每一步都打断用户，也让用户在关键决策上拥有控制权。

## 交互原则三：解释要服务于验证

“可解释”不是把所有内部日志都暴露出来，而是帮助用户判断结果是否可以使用。我将解释信息分成三层：

1. **结论层**：结果、图表和关键结论；
2. **依据层**：指标定义、筛选条件、时间范围、数据来源；
3. **过程层**：任务节点、工具调用、校验状态和异常原因。

默认展示结论层，用户需要核对时再展开依据层和过程层，形成渐进式披露。
