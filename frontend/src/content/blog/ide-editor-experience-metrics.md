IDE 和运维控制台都有导航、表格、日志和状态反馈，但体验目标不同。

控制台帮助用户安全地完成一项操作；IDE 承载持续的开发过程。用户会反复经历理解、编辑、运行、诊断和修改，很难用一次点击或一个页面衡量体验。

本文选择两类数据开发 IDE：**SQL 编辑器**和**任务流编排编辑器**。前者以输入和执行为主，后者以画布编排和调试为主，分别代表键盘密集型与图形操作型工具。

## IDE 与控制台的度量差异

控制台强调准确完成操作，IDE 强调持续推进工作。

| 维度 | 运维控制台 | IDE 编辑器 |
| --- | --- | --- |
| 典型任务 | 创建资源、修改配置 | 编辑、运行、诊断、修正 |
| 工作节奏 | 任务相对独立 | 长时间连续工作 |
| 核心风险 | 误操作、配置失败 | 思路中断、反馈延迟、修改失控 |
| 效率表现 | 更少步骤完成操作 | 更少打断地完成开发循环 |

因此，停留时间长不一定代表 IDE 难用，文件或面板切换多也不一定代表流程绕远。指标必须放在具体任务中解释。

## 用开发循环作为度量单位

IDE 的基本单位不是页面，而是一次开发循环：

1. 找到目标位置。
2. 理解相关数据或依赖。
3. 完成编辑。
4. 执行、预览或测试。
5. 根据反馈继续修改，或确认结果。

体验问题通常表现为循环被打断：搜索不准确、补全太慢、错误定位不到源码，或用户无法确认运行的是不是最新版本。

因此，需要关注一次有效修改经历了多少轮尝试、等待占用多少时间，以及用户被迫离开当前上下文多少次。

## 用 KLM 建立操作基线

击键层次模型（KLM）用于预测熟练用户按既定方法完成任务的时间。它由 Card、Moran 和 Newell 提出（[原始论文](https://dl.acm.org/doi/10.1145/358886.358895)）。

基础公式为：

`T = K × tK + P × tP + H × tH + M × tM + ΣR`

K 是按键，P 是指针定位，H 是键鼠切换，M 是执行动作前的思考准备，R 是系统等待。任务流编排还可加入 D（拖拽）。各项时间最好用目标用户和实际设备测量，不必照搬通用常数。

KLM 只描述熟练用户在路径已知、没有错误时的理论时间。它不适合解释代码理解和调试探索。因此，应把 KLM 当作基线，再记录真实使用中的损耗。

| 指标 | 计算方式 | 反映的问题 |
| --- | --- | --- |
| KLM 理论时间 | 各操作符时间之和 | 交互路径是否精简 |
| 时间偏离率 | `(实测时间－KLM 时间) ÷ KLM 时间` | 用户是否被流程阻塞 |
| 系统等待占比 | `ΣR ÷ 实测总时间` | 响应是否拖慢开发循环 |
| 无效操作率 | 无效操作数 ÷ 总操作数 | 操作是否易错或结果不可信 |
| 恢复时间 | 错误出现到重新有效编辑的时间 | 容错与恢复能力 |

理论路径很短但实测仍慢，问题通常在反馈、理解或恢复；理论路径本身就长，则应先简化交互。

## 一套可执行的评分标准

团队可以选取 5～8 个高频任务，统一数据、起始状态、目标结果和设备环境。

| 评分项 | 权重 | 满分条件 | 需要改进 |
| --- | ---: | --- | --- |
| 任务成功 | 25 | 无协助成功率 ≥ 95% | 低于 85% |
| 操作效率 | 25 | 实测中位时间 ≤ KLM 的 1.25 倍 | 超过 1.6 倍 |
| 系统响应 | 20 | 等待占比 ≤ 15% | 超过 30% |
| 操作准确 | 15 | 无效操作率 ≤ 5% | 超过 12% |
| 上下文连续 | 15 | 没有非必要中断 | 频繁离开任务或丢失位置 |

中间区间按比例计分。这些阈值是团队校准的起点，不是跨产品的行业标准。得分适合比较同一任务在不同版本或方案中的变化。

## SQL 编辑器如何评测

SQL 编辑器的循环是理解表结构、编写查询、执行、阅读结果和修正错误。

| 标准任务 | 完成标准 | 重点记录 |
| --- | --- | --- |
| 编写筛选查询 | 返回正确记录 | 输入、补全、执行次数 |
| 多表关联查询 | 字段和关联条件正确 | 查结构、跳转和改写次数 |
| 修复语法错误 | 成功执行且结果正确 | 报错到有效修改的时间 |
| 定位数据异常 | 找到记录并解释原因 | 查询轮次和上下文切换 |
| 修改并重新执行 | 新结果对应最新 SQL | 重复执行和版本确认 |

设计师可以记录：首次正确结果时间、执行与失败次数、错误恢复时间、重复打开表结构的次数，以及用户对结果正确性的信心。

重复执行不一定无效。如果每次都在验证新假设，应视为正常探索；只有重复相同操作却没有获得新信息，才记为无效。

## 任务流编排编辑器如何评测

任务流编排包含指向、拖拽、连线、配置和运行。

| 标准任务 | 完成标准 | 重点记录 |
| --- | --- | --- |
| 创建三节点流程 | 节点、顺序和连线正确 | 搜索、拖拽、连线时间 |
| 配置节点参数 | 必填项完整且格式正确 | 面板切换和校验失败 |
| 修改上下游依赖 | 依赖更新且无断链 | 误连、重建和撤销次数 |
| 定位失败节点 | 找到根因并进入正确配置 | 反馈到有效修改的时间 |
| 从失败处重跑 | 恢复且不重复成功节点 | 重跑范围判断和等待 |

设计师可以记录：正确节点与连线比例、误连和无效拖拽次数、失败定位时间、配置面板与日志打开次数，以及用户判断重跑范围的正确率。

缩放、平移和重排不一定是损耗。只有这些操作没有帮助理解，只是在找回位置时，才计为上下文中断。

## 设计师可以直接采集的指标

多数指标可以通过任务脚本、屏幕录制、操作观察和简短问卷获得，不必先建设复杂埋点。

| 指标 | 采集方式 | 用途 |
| --- | --- | --- |
| 任务成功率 | 记录成功、部分成功、失败 | 判断方案能否支持任务 |
| 完成时间 | 从读完任务到结果正确 | 比较版本或方案效率 |
| 首次有效结果时间 | 标记第一次可继续判断的结果 | 衡量反馈回路长度 |
| 无效操作数 | 回看录屏并按规则标记 | 定位误导和重复操作 |
| 错误恢复时间 | 标记报错和下一次有效执行 | 衡量容错能力 |
| 上下文中断数 | 记录无效切页和外部切换 | 衡量思路连续性 |
| SEQ 单题易用度 | 每个任务后询问，1～7 分 | 补充主观难度 |
| 结果信心 | 完成后询问，1～5 分 | 衡量结果可信度 |

其中，任务成功率、完成时间、无效操作数和恢复时间适合作为核心客观指标；SEQ 和结果信心用于解释主观差异。一次测试选择 4～6 项即可。

设计师可为每位参与者、每个任务记录一行：

| 参与者 | 任务 | 成功状态 | 完成时间 | KLM 时间 | 无效操作 | 恢复时间 | 中断次数 | SEQ | 信心 |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| P01 | 修复 SQL 字段错误 | 成功 | 48s | 31s | 3 | 19s | 1 | 5 | 4 |
| P02 | 定位失败节点并重跑 | 部分成功 | 126s | 72s | 7 | 54s | 3 | 3 | 2 |

先看任务是否成功，再看时间和操作损耗，最后结合录屏解释原因。小样本更适合发现问题；追踪版本趋势时，需要持续使用同一套任务和记录口径。

## 用相对基线比较两类编辑器

SQL 查询和任务流编排的复杂度不同，不应直接比较绝对耗时。更合理的是分别计算相对 KLM 基线的偏离率，再判断损耗来自哪里。

| 对比维度 | SQL 编辑器 | 任务流编排编辑器 |
| --- | --- | --- |
| 主要操作 | 输入、补全、跳转、执行 | 指向、拖拽、配置、连线 |
| 主要等待 | 查询和结果加载 | 调度、节点运行、日志聚合 |
| 常见损耗 | 重复执行、误补全、反复查结构 | 误连、重排、重复打开配置 |
| 关键恢复 | 保留 SQL 和结果版本 | 定位失败节点并按范围重跑 |
| 信任问题 | 结果是否对应当前语句 | 运行状态和依赖影响是否清楚 |

最终可以分别生成 SQL 编辑体验分和任务流编排体验分。总分用于看趋势，任务明细用于指导设计改进。

## 结语

运维控制台追求安全、准确地完成操作；IDE 追求保持思路，并缩短从编辑到反馈的距离。

体验度量除了问“任务完成了吗”，还应记录中断、等待、无效操作和恢复。把这些数据放回 SQL 编写与任务流编排的真实循环中，指标才会对设计有用。
