## 什么是 DESIGN.md
Google Stitch 团队在 2026 年初公开了 `DESIGN.md` 的 draft specification，将其定义为一种向 Coding Agent 描述视觉身份和设计系统的纯文本格式。

它本质上是一份同时面向设计师、工程师和 AI Agent 的设计规范：既可以记录颜色、字体、间距和圆角等机器可读的 Design Token，也可以用自然语言解释这些规则为什么存在、适用于什么场景，以及发生冲突时应该如何取舍。

在实际项目中，一份较完整的 DESIGN.md 还可以涵盖品牌视觉方向、布局与组件规则、Hover、Focus、Loading 等交互状态，以及推荐做法、禁止模式和例外范围。

因此，DESIGN.md 并不是简单地把 UI 规范改写成 Markdown。它更重要的作用，是补充 Token 无法表达的设计意图和使用边界，让设计方案、代码实现与 AI 生成结果收敛到同一套标准上。

需要注意的是，Google 当前公开的规范仍处于 alpha 阶段，格式和 Token Schema 还可能继续变化。现阶段更适合把它理解为一种正在形成中的方法，而不是已经稳定的行业标准。



## 能解决什么问题
1. **减少 AI 自由发挥**：当设计规则没有被明确记录时，AI 往往会选择一套通用的生成模式，例如大圆角、毛玻璃、装饰性渐变、层层嵌套的卡片、超大标题，以及未经定义的新颜色。将允许使用的设计元素、禁止模式和例外条件写进 DESIGN.md，可以让 Agent 在既定范围内做判断，而不是每次根据局部代码或通用经验重新猜测。
2. **统一分散的设计规则**：同一套设计规范通常同时存在于 Figma、组件库、设计文档和团队成员经验中，很容易出现偏差。DSEIGN.md 能把这些规则集中到一处文档中，并标注每条规则对应的代码位置，包括 Token、基础样式、组件样式、动效规则等。
3. **补充 Token 无法表达的设计意图**：比如 --radius-container: 8px 只能说明容器的圆角数值，但解释不了为什么用 8px；而文档里补一句「容器使用 8px 圆角，保持一定舒适度，同时避免消费级产品常见的大圆角」，设计意图就完整了。Token 负责管理数值，文档负责解释使用方式。
4. **让“设计是否一致”可以被检查**：抽象的一致性无从验证，但具体规则可以：是否出现硬编码颜色、是否绕过语义 Token、是否用了未经允许的 Tailwind 默认色、组件有没有 Focus 状态、Hover 会不会改变尺寸、Token 是否缺失。写到这个程度之后，DESIGN.md 就不只是一份设计说明，也可以成为视觉 QA 和代码检查的依据。



## Google 和 Vercel 怎么做
Google 和 Vercel 展示了 DESIGN.md 的两类重点：

|  | Google | Vercel |
| --- | --- | --- |
| 核心问题 | 设计信息应该用什么格式表达 | Agent 应该如何做设计决策 |
| 主要内容 | 结构化 Token 与设计说明 | 任务判断、决策顺序、禁止模式和验收方式 |
| 精确数值 | 可以直接写入 YAML Front Matter | 主要由外部 CSS 和设计系统提供 |
| 侧重点 | 格式与机器可读性 | 场景、取舍与执行边界 |


简单来说，Google 更关注“如何让人和工具读取同一份设计信息”，Vercel 更关注“Agent 在真实任务中应该怎样理解材料、处理冲突并完成实现”。前者提供格式、后者提供决策方法

### Google：把格式标准化
[google-labs-code/design.md](https://github.com/google-labs-code/design.md)

Google 将 DESIGN.md 定义为一种向 Coding Agent 描述视觉身份和设计系统的文本格式。它由两层内容组成：

+ **YAML Front Matter**：记录机器可读的 Design Token，为颜色、字体、字号、间距和圆角等提供精确值；
+ **Markdown 正文**：解释视觉方向、使用场景、设计意图和取舍理由。


下面是一个基于 Google 规范整理的简化示例：

```css
/* 采用 Public Sans 字体、标题为深水墨色、背景为暖石灰石色,
   并配有 BostonClay 字体的号召性用于按钮。  */

---
version: alpha
name: Data Workbench
description: A calm, precise interface for long-running data work.
colors:
primary: "oklch(55% 0.14 252)"
on-primary: "#ffffff"
background: "oklch(96.5% 0.004 252)"
foreground: "oklch(25% 0.004 252)"
border: "oklch(85.8% 0.007 252)"
typography:
body-md:
fontFamily: Inter
fontSize: 1rem
fontWeight: 400
lineHeight: 1.5
rounded:
control: 6px
container: 8px
spacing:
xs: 0.25rem
sm: 0.5rem
md: 1rem
components:
button-primary:
backgroundColor: "{colors.primary}"
textColor: "{colors.on-primary}"
typography: "{typography.body-md}"
rounded: "{rounded.control}"
padding: 0.75rem
---

## Overview

Architectural Minimalism meets Journalistic Gravitas. The UI evokes a
premium matte finish — a high-end broadsheet or contemporary gallery.

## Colors

The palette is rooted in high-contrast neutrals and a single accent color.

- **Primary (#1A1C1E):** Deep ink for headlines and core text.
- **Secondary (#6C7278):** Sophisticated slate for borders, captions, metadata.
- **Tertiary (#B8422E):** "Boston Clay" — the sole driver for interaction.
- **Neutral (#F7F5F2):** Warm limestone foundation, softer than pure white.
```



Google 规范约定的正文章节依次包括 Overview、Colors、Typography、Layout、Elevation & Depth、Shapes、Components、Do's and Don'ts。章节可以按需省略，也可以保留规范尚未定义的扩展内容。

除了格式定义，Google 还提供了 lint、diff 和 export 等能力，用于检查 Token 引用、对比度、章节结构和版本差异。这使 `DESIGN.md` 不只是供 Agent 阅读的提示词，也具备了成为工程资产的基础。



### Vercel：把设计决策写得更具体
[https://vercel.com/design.md](https://vercel.com/design.md)

Vercel 的 DESIGN.md 面向于一个明确的场景：设计和实现由 Vercel 品牌署名的<u>报告型网站</u>，包括客户报告、提案、基准分析、比较页面和计算器等需要数据叙事的页面。

与 Google 的方式不同，Vercel 将精确的颜色、间距、圆角等数值放在外部的 [vercel-brand.css](https://vercel.com/geist/vercel-brand.css) 中，DESIGN.md 则负责解释如何组合这些能力、何时允许扩展，以及哪些实现必须拒绝。

两者形成明显的分工：
+ CSS：精确 Design Token、主题、组件状态等
+ DESGIN.md：适用范围、决策顺序、设计意图、适用边界、验收方式


Vercel 有三个值得借鉴的地方：

1. **先规定决策方式，再描述视觉结果**：当要求发生冲突时，Agent 首先保护用户的明确目标和实际约束，再考虑交付框架、信息结构、品牌识别和细节优化。这样的优先级意味着，“设计得像 Vercel”并不是最高目标。如果品牌表现会损害实际任务、阅读效率或已有工程约束，就应该让位。

2. **将执行过程拆成一条四步决策链：**理解用户任务 → 识别信息关系和排版 → 设计系统约束和实现 → 检查对齐和阅读效果
    - **理解用户任务**：明确 5W1H，比如一个模型评估页面的用户任务是比较多个模型的准确率、成本和响应速度、决定哪一个可以发布，而非查看模型指标
    - **根据任务选择版式**：这里最重要的原则是先选择几何关系再选择组件。 版<u>式不从现成的模版中选择</u>、而由于信息关系决定。比如首屏用户任务是做出明确决定、则需要将结论或关键一句并列，如需比较多个方案则需要实用相同尺寸的对照布局，如需查看趋势则让变化关系成为视觉中心等。随后把信息关系转成视觉关系，比如定性比较用对齐的行或列、时间变化用水平顺序等。
    - **设计系统约束实现**：版式确定后设计系统开始介入，用于保证已经确定的内容结构能够一致、可访问、可维护，包括品牌外壳、响应式、字号层级、颜色、空间交互、动效图标等约束。
    - **对齐方式和检查**：第一眼是否看见核心关系 → 构图是否有主次 → 字体间距是否一致 → 数据几何是否真实表达结论 → 是否存在可以删除的装饰 → 响应式和主题是否保持 → 无障碍是否准确

3. **通过大量禁止规则排除 Agent 生成的默认样式**，包括装饰性渐变、光晕、玻璃拟态、居中 Hero 加卡片阵列、嵌套面板、普通元数据胶囊、无意义图标底座和没有统一尺度的装饰图表。它甚至规定检查工作应在内部完成，最终交付实现结果，而不是附带评分、过程日志和自我评价。这里的重点不是照搬黑白配色，而是用明确的非目标保护信息层级和设计判断。


## DESIGN.md 实践
这次实践的背景，是重构一个承载高密度数据浏览和分析的 AI 数据产品。产品前期通过 Vibe Coding 快速完成了功能和页面，但生成结果也带入了常见的通用样式：大圆角、大标题、卡片嵌套和偏装饰性的层级。随着功能持续叠加，颜色、间距、圆角、组件状态和页面密度开始在不同模块中分化。

因此，在没有设计系统的前提下，需要用 DESIGN.md 为这次**重新设计并建立一套可被 AI 共同读取的设计约束**，负责说明视觉方向、样式定义、语义关系、组件状态、禁止模式、例外范围。

### 核心内容结构设计
DESIGN.md 核心结构综合借鉴了 Google 与 Vercel 的组织方法，按「**为什么这样设计、界面如何表现、怎样实现、如何检查**」顺序组织，表达设计意图、实现方式和规则约束。

```plain
品牌视觉语言
    ↓
视觉语法 + 交互语法
    ↓
设计 Token
    ↓
布局 + UI 模式
    ↓
图标 / 图表 / 入口页 / 响应式
    ↓
实现锚点 + 契约 + 反模式 + 结构测试
```

+ 品牌视觉语言：用来说明产品定位、品牌支柱、信息密度和明确禁止的视觉模式；
+ 视觉语法与交互语法：把抽象方向转换为表面层级、圆角、Hover、Focus、动效、表单和浮层等通用规则；
+ 设计 Token ：位于中间，负责为颜色、排版、间距、圆角、主题强调色和组件状态提供精确值与语义名称；
+ 布局和 UI 模式：规定工作台壳层、多栏布局、按钮、输入框、表格、卡片、Loading 等常见场景如何组合；
+ 其他：图标、图表、入口页和响应式则处理产品中具有领域特点或设备差异的具体问题；
+ 反模式约束和检查：说明规则哪些做法必须拒绝，以及如何检查文档与实现是否保持一致。



### 明确品牌视觉和交互语法
我将产品定位为一个冷静、精确、长时间使用的数据工作台。因此界面使用低饱和蓝灰、紧凑的信息密度和克制的圆角，主要依靠灰阶、边框和排版建立层级，紧凑但不拥挤的信息密度服务于数据扫描，点阵和局部像素硬边用于品牌识别。

**视觉语法**：规定页面底、内容面、弱强调面和控件轨道的层级关系。列表和表格优先于卡片墙，密集区域使用较小间距，页面壳层和主要面板保留适当留白。层级优先通过灰阶、描边和间距表达，减少阴影和多层卡片；工作台切分边界可以使用直角，但不作为普通组件的默认样式。

**交互语法**：规定各类状态如何变化：普通 Hover 使用灰底、实线边框或图标变色，Focus 和浮层打开时使用更明确的描边与 Focus Ring，删除等破坏性操作需要二次确认。动效只用于状态反馈，不能改变布局占位，并在 `prefers-reduced-motion` 下关闭非必要动画。产品当前只提供浅色模式，不使用霓虹渐变、玻璃拟态、大圆角卡片墙、Emoji 功能图标和全屏旋转 Loading。这些规则为后续新增页面和组件提供统一边界。



### 从 HSL 迁移到 OKLCH
过去团队表达颜色的方式一般会采用 RGB 或 HSL：

+ **RGB** ：直接描述红、绿、蓝三个通道的组合，与屏幕显示最接近、兼容性也稳定，但很难直接回答「这个颜色应该亮一点、鲜艳一点」之类的问题，不太适合用在设计系统中进行批量生成颜色色阶。

```css
color: rgb(38 41 48);
background: rgb(245 247 250 / 80%);
```



+ **HSL**： 将颜色拆成色相 H、饱和度 S 和亮度 L，相比 RGB 它更符合人工调色的思维方式，修改 H 可以快速切换红黄蓝色相、修改 L 可以生成看起来有明暗规律的颜色色阶。但 HSL 有个致命问题是，两个不同的颜色即使使用相同的亮度、在人眼看来也可能有明显的不同，黄色一般会显得比蓝色亮得多；类似的，相同饱和度的不同颜色，看起来也不一样。

```css
--blue: hsl(240 80% 50%);
--yellow: hsl(60 80% 50%);
```



这里我选择了用更适合建立 Design Token 的 **OKLCH** 色彩体系。它与 HSL 类似，将颜色拆成感知明度 L、饱和度 C、色相 H。而它优势是弥补 HSL 的不足，能确保相同明度和饱和度的不同颜色色相、在人眼看来能几乎接近。设计灰度色阶和主题色时，可以先稳定明度层级和色度范围，再调整色相，能够得到更可控的主题起点。

```css
:root {
  --theme-hue: 252;

  --gray-150: oklch(0.965 0.004 var(--theme-hue));
  --gray-400: oklch(0.858 0.004 var(--theme-hue));
  --gray-900: oklch(0.25 0.004 var(--theme-hue));
}
```

当主题从蓝色切换为绿色或橙色时，主要修改 `--theme-hue`，可以保留原有的明度结构和低饱和倾向。这里强调的是“更稳定的起点”，而不是“只改色相就一定得到完全一致的主题”。不同色相仍可能出现感知差异、色域裁切和对比度变化，因此每个主题都需要单独检查文本对比度、状态辨识度和真实屏幕效果。



### 从 px 迁移到 rem
团队过去习惯使用 px 作为 UI 元素尺寸间距的计量单位，因为它与设计稿标注直接对应，局部实现也容易核对。

但长此以往，间距会逐渐出现 10px、14px、18px、22px 等相近但不统一的取值，字号、图标、表单和容器也容易形成彼此独立的尺度。问题在于缺少有限、共享的空间阶梯。

而 rem 可以很好的解决这个问题，它可以基于根像素计算尺寸和间距，让内容和阅读节奏共享一个尺度

+ 间距可以随着根字号一起变化。用户放大字体后，文字和空间比例不会明显失衡。
+ 间距与内容关系更紧密。文字、图标、表单和卡片内边距都可以使用同一套尺度。

```plain
--space-1: 0.25rem; /* 4px */
--space-2: 0.5rem;  /* 8px */
--space-3: 0.75rem; /* 12px */
--space-4: 1rem;    /* 16px */
--space-5: 1.25rem; /* 20px */
--space-6: 1.5rem;  /* 24px */
--space-8: 2rem;    /* 32px */
```



但不需要所有尺寸都使用 rem，如：边框使用 1px、控件圆角使用 6px、顶栏高度使用 56px 等依然可以保留 px

我的原则是：与内容和阅读尺度相关的尺寸使用 rem；与描边和固定组件形状相关的尺寸可以使用 px。



### 设计语义 Token
颜色和间距模型调整后，组件仍然不会直接读取基础颜色。

Design Token 核心结构分为基础值、语义角色和组件使用三层，把具体数值、设计含义、组件实现分开管理，让设计系统更容易调整、扩展和维护。

```css
:root {
   /*基础Token*/
  --gray-0: oklch(1 0 0);                              
  --gray-150: oklch(0.965 0.004 var(--theme-hue));
  --gray-400: oklch(0.858 0.007 var(--theme-hue));
  --gray-900: oklch(0.25 0.004 var(--theme-hue));
  
 /*语义Token*/
  --background: var(--gray-150);
  --surface: var(--gray-0);
  --foreground: var(--gray-900);
  --border: var(--gray-400);
}
```

组件最终使用：<div className="bg-background text-foreground">

这样设计 Token 的好处是

+ **降低耦合**：组件不直接依赖具体色值、调整任何颜色不必逐个修改组件。
+ **表达意图**：background、border 比 blue-600、yellow-400 更容易理解设计意图，并正确使用。
+ **方便换主题**：只需重新映射语义 Token，不需要重写组件样式。
+ **统一组件状态**：按钮、输入框等可以集中管理 Hover、Focus、Disabled 等规则。
+ **约束 AI 生成**：AI 只需选择明确的语义或组件 Token，不必自行猜测



### 把交互状态写成组件契约
重构前，很多组件的默认样式已经基本统一，但一进入交互状态，差异就会暴露出来：输入框 Hover 有的出现虚线、有的出现阴影；菜单项有的使用灰色背景、有的增加边框；图标按钮会分别改变背景、边框或图标颜色。

问题在于没有说明「这一类组件在什么状态下应该怎样变化」，导致 AI 在生成新页面时通常会沿用当前页面附近的写法，使同一种组件继续产生新的状态变体。因此，需要把交互规则从零散样式整理成组件契约。

常规的设计系统就是先建立一套共用的状态顺序：默认状态保持安静，Hover 表示组件可以操作，Focus 或浮层打开表示当前操作位置，Selected 表示结果已经生效，Disabled 表示暂时不可操作，Error 和 Loading 则分别说明异常与处理中。不同类型的组件状态可能存在不同反馈，需要建立一套面向 AI 生成的统一交互规则。

以 Hover 为例菜单项、表格行和次级按钮使用浅灰背景，因为它们需要反馈当前指向的行或操作；输入框、选择器、树节点和内联编辑器使用实线边框，因为边界变化更能表达“这里可以输入或编辑”；无边框图标按钮只改变图标颜色，避免每个小操作都出现新的表面；可点击卡片允许强化边框并轻微上移，但不增加大阴影。无论使用哪种反馈，都不能改变组件尺寸和布局占位，也不能让 Hover 成为唯一提示，因为触屏设备没有稳定的 Hover。



### 值得进一步优先改进
当前的 DesignToken、 组件规则已经比较完整，对“页面为什么采用这种结构”约束较少，下一步重点应从「补充更多规则」转向「消除冲突、减少重复，并让规范可自动检查」，可以增加如：

+ 精确查找数据时优先使用表格
+ 比较方案时使用相同尺度和对齐方式
+ 长任务把状态和进度放在主要阅读路径上
+ 不默认生成“居中标题 + 指标卡片 + 卡片网格”

补足从用户任务到设计系决策之间的环节。



## 总结：从设计文档到设计契约
Google 为 DESIGN.md 提供了一种基础范式：用结构化数据记录精确的 Design Token，用自然语言解释设计意图、使用场景和取舍原则。

Vercel 的实践则进一步表明，一份真正有效的规范不能止于颜色、字号和间距，还需要回答几个更关键的问题：

+ 面对具体任务时，应该如何选择信息结构和页面布局；
+ 当品牌表达、用户需求与工程约束发生冲突时，什么应当优先；
+ 哪些组件状态、视觉模式和实现方式可以使用，哪些必须拒绝；
+ 如何检查最终结果是否符合规范。

而在这次实践中，通过 OKLCH、rem 和语义 Token 建立了更稳定的视觉基础，也将 Hover、Focus、Loading、Error 等状态整理为组件契约，并通过代码锚点和结构测试，让规范能够与实现保持同步。

但更重要的收获是：`DESIGN.md` 的价值不在于收录多少规则，而在于能否把隐性的设计经验转化为可理解、可执行、可检查的共同约束。它既要告诉团队“界面应该是什么样”，也要解释为什么这样设计、应该如何实现，以及出现例外时如何判断。

因此，`DESIGN.md` 不应被看作一份更长的 UI 说明书，而应成为设计师、工程师和 AI Agent 共同使用的设计契约。它连接设计意图与代码实现，减少重复决策，也让 AI 生成从“模仿某种风格”转向“遵循明确的设计逻辑”。

对于一般项目，没有必要一开始就建立一套庞大的规范。更合适的方式是从最容易反复失控的部分开始，例如：

```plain
1. 产品与品牌方向
2. 核心设计原则与决策优先级
3. 明确禁止的设计模式
4. 颜色、排版、间距与圆角 Token
5. 表面层级与常用布局
6. 组件及其交互状态
7. Loading、Empty、Error 等系统状态
8. 响应式与可访问性
9. 实现文件与代码锚点
10. 例外、遗留规则与检查方式
```

当某类问题反复出现，再将解决它的判断标准补充进文档。这样，`DESIGN.md` 才不会变成不断膨胀却无人使用的规则合集，而会随着产品演进，逐渐沉淀为一套真正可执行的设计决策系统。
